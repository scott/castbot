# S07b approval cards

A web turn that asks for a tool shows one approval card in the chat. The card names the tool, the time in the user's zone, and the arguments with secret values replaced by Hidden. Approve and Deny are the only actions. Deny is the only danger button. A second click, or a click from another tab, changes nothing: one permission response and one audit row. A card that the agent no longer has pending becomes inactive and says the request is no longer active.

The server owns the wait. The default is 10 minutes, and `CASTBOT_APPROVAL_TIMEOUT` can set it (at least 1 second, at most 24 hours). When the wait ends, the server posts a denial, marks the card expired, and writes an audit row for `system:timeout`. Closing the browser stream does not deny the card. The same card is there after a reconnect. A paused machine is woken on the click, then the decision is posted. An expiry or a restart denial does not wake a paused machine, and a denial that keeps failing waits longer between tries (2 seconds, then 4, 8, 16, 32, capped at 60) with its own 15 second deadline. Schema version 13 adds `approvals` and `audit_log`. Version 12 stays the real runtime migration.

The click checks the run id before it claims the row. Claim, the permission response, and the audit row run on a server context, so a tab that closes mid-click still lands the decision when the agent accepts it. If that post fails, the claim returns to pending and a later click or the timeout can try again. On startup, and every second after a 30 second grace, a row that was claimed and not confirmed is posted again and then audited. A lost request is marked inactive and does not write `approval.approved`. A claim whose run has already failed is denied if the guest is still waiting, then marked inactive, and it does not write `approval.approved`. The one second loop still marks rows due while a post is in flight, and each sweep posts one denial and one recovery.

A bundle publish or a secret change does not restart the guest while a web approval is pending, while another run is still open, or while this run has already started (`waiting_approval`, or a stream offset above 0). The restart waits until that run finishes. The next message applies it before the new turn, because a brand new run with offset 0 is left out of the check. Opening the agent page or saving the agent waits the same way while any run is streaming or waiting. A wait is logged only when a bundle or a secret change is actually pending, once per change of that wait, with its reason and an 8 character prefix of the old and new secret fingerprint. The 15 minute bound starts at that first wait, not at the run's start. A pending web approval is never forced; its own timeout ends that wait. A tool the user just approved is never forced either: while that run is still open and has had no event since the approval's permission event, the tool result has not arrived and the wait goes on. The tool result, or the end of the run, ends that guard. After that, a wait that has already passed 15 minutes proceeds, and that forced restart is logged once.

A run that was left open at shutdown has its pending cards marked inactive. The expiry loop posts Deny when the machine is still reachable, and it does not wake a paused one. After a decision the run returns to streaming while the tool continues. The waiting bar, the sidebar badge, and the nav count refresh with the card.

Secret names match whole segments. Names are split at camelCase, at the end of a run of capitals, and before digits, so `APIToken` reads as `api_token`, `DBPassword` as `db_password`, `SSHKey` as `ssh_key`, and `password2` as `password_2`. A trailing `keys` reads like `key`, so `apiKeys` and `access_keys` are hidden. A name that ends in `_key` is hidden unless it is on a short allow list: `sort_key`, `cache_key`, `object_key`, `partition_key`, `primary_key`, `idempotency_key`, `host_key`, and any name ending in `public_key` (such as `ssh_public_key` and `client_public_key`), including camelCase. `pw`, `pwd`, `passwords`, `secrets`, and `assertion` are hidden segments too. `pass` is judged after dropping trailing number, version, encoding, and environment words, so `db_pass_prod`, `DB_PASS2`, `user_pass_v2`, and `pass_b64` read as `db_pass`, `db_pass`, `user_pass`, and `pass`. It is hidden on its own, at the end of a name (`db_pass`, `test_pass`), and before any word that is not a known non-secret word (`pass_word`, `pass_env`), while `pass_rate`, `pass_count`, `pass_through`, `first_pass`, `last_pass`, `passage`, and `bypass` stay visible. A key followed by a number, version, encoding, or environment word is still a key, so `ssh_key2`, `signing_key_v2`, `signing_key_b64`, `encryption_key_hex`, `aws_key_1`, `stripe_key_live`, and `deploy_key_pem` are hidden. `cookie` and `cookies` at the end of a name (`session_cookie`, `Set-Cookie`) are hidden, while `cookie_name` and `cookie_domain` stay visible. The public key exemption does not apply when a secret word comes first, so `secret_public_key` and `private_public_key` are hidden. `auth`, `pass`, `jwt`, `pat`, `bearer`, `basic_auth`, and `auth_header` are hidden. Token counts stay visible: a name made only of token-count words (`tokens`, `num_tokens`, `token_count`, `max_tokens`, `input_token_count`, `max_tokens_to_sample`, `cached_tokens`, `reasoning_tokens`). `read`, `write`, and `new` are not enough on their own, so `read_tokens`, `write_tokens`, and `new_tokens` are hidden while `max_new_tokens`, `cache_read_input_tokens`, and rates such as `tokens_per_second` stay visible. Any other word keeps it hidden, so `access_tokens`, `max_secret`, and `secret_count` are hidden. `auth_mode`, `auth_type`, `auth_method`, and `auth_scheme` name a scheme and stay visible; `auth`, `auth_code`, and `auth_header` do not. Ordinary names such as `session`, `tokenizer`, and `secretary` stay visible. `env` and `headers` stay hidden. A bearer token inside a command string or an array is replaced with `Bearer Hidden` and the rest of the argument stays. Argument text is clipped at 80 runes so a long value stays valid UTF-8.

An approval that arrived from a Cast CLI journal is read only. It has no buttons. The real journal writes the decision before the permission, with an empty session and no tool name. The tool is copied from the matching permission, and the decision is attached to that permission's thread so it does not open a second Cast CLI thread. The thread shows the ask, then the decision. A web turn's own journal (caller `control_plane` on the web thread) is not copied in as a second card. A recovery of a claim whose run has already failed posts Deny when the guest is still waiting and marks the row inactive. It does not post Approve and it does not write `approval.approved`. Recovery always posts the decision again. castlet journals every decision before it forwards it to the runtime, including that re-post, so a journal row alone does not prove delivery. Before the re-post, recovery pulls the castlet journal and notes the decision it already holds for that request, on the agent's current machine only. If the re-post finds no pending prompt, only that earlier state counts, never the row the re-post just added. A decision that was already there means an earlier post was delivered: the row is audited with its own status and marked sent. On a failed or stopped run a lost prompt is never audited as approved; Deny is posted and the row is inactive. A journal decision that disagrees with the row is logged and does not change the row. A request the agent no longer has, with no journaled decision, is inactive on that path too. The waiting bar and badges are sent again on the stream event that follows the decision, including the done event, so a click whose card was already swapped still clears them. Another user's card, run, and event stream are 404, and the body does not include the command or the approval id.
